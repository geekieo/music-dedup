# MusicDedup

本地重复音乐管理工具，支持千万级音乐库。

**纯 JavaScript 声纹识别**，无需安装任何外部工具。基于 Goertzel 频谱指纹算法，识别同一录音的不同格式与音质版本，结合智能保留规则自动决策。

---

## 快速开始

**环境要求：Node.js ≥ 18**

```bash
npm install
npm start
```

浏览器打开 **http://localhost:3456**

## 使用流程

1. **设置** — 点击"添加文件夹"，从系统对话框中选择音乐库目录
2. **扫描** — 开始扫描，实时查看进度，随时可暂停/继续/停止
3. **重复组** — 查看发现的重复组，确认删除方案
4. **确认** — 文件移入系统回收站，可撤销

## 核心功能

| 功能 | 说明 |
|------|------|
| 纯 JS 声纹识别 | Goertzel 频谱指纹，无需外部工具，识别同一录音的不同格式/音质 |
| 多阶段检测 | 精确指纹匹配 → 标题匹配 → 指纹前缀 LSH → 时长分桶，逐层扩大召回 |
| 智能保留 | 音质优先 → 首发专辑 → 单曲/专辑判断 → 元数据完整性 |
| 手动覆盖 | 点击任意曲目图标，覆盖自动建议 |
| 批量操作 | 一键确认所有待处理重复组 |
| 安全删除 | 移入系统回收站，不立即永久删除 |
| 实时进度 | SSE 推送扫描进度，多客户端同时可见 |
| 暂停 / 继续 / 停止 | 扫描中任意阶段都可暂停（保留进度，原地等待）或直接停止 |
| 自动保存 | 设置修改后 700ms 防抖自动保存；声纹阈值/时长容差/音质优先级的改动需要在"扫描"页手动点击智能执行才会重新匹配，避免后台静默触发与手动操作冲突 |

## 重复判断逻辑

### 识别阶段（4 阶段）

| 阶段 | 方法 | 说明 |
|------|------|------|
| 1 | 精确指纹匹配 | 指纹字符串完全相同 → 必定重复，无需阈值 |
| 2 | 标题匹配 | 从元数据或文件名提取歌名，归组后比对指纹 |
| 3 | 指纹前缀 LSH | 相同音频前缀整数相同，归组后比对全指纹 |
| 4 | 时长分桶 | 相同时长（±4s）归组，比对指纹 |

### 保留策略（优先级）

1. **音质最优** — Hi-Res FLAC > FLAC > WAV > M4A > MP3 320k > …
2. **首发专辑** — 年份最早的正式专辑（合辑不算）
3. **单曲 vs 专辑** — 本地专辑 ≥ 2 首保留专辑版；否则保留单曲版
4. **元数据完整性** — 标签最完整的文件

## 声纹算法说明

基于 **Goertzel 频谱指纹**（Sub-band Spectral Fingerprinting）：

1. 将音频解码为 PCM（支持 MP3、FLAC、M4A、OGG、WAV 等格式）
2. 重采样至 11025 Hz 单声道
3. 用 Goertzel 算法计算 33 个对数均匀分布频率（300 Hz–2 kHz）的能量
4. 比较相邻帧的频谱斜率变化方向 → 32 位整数
5. 120 个整数构成指纹（约 1 秒音频，快速且可靠）

相似度计算：对两个整数数组逐位做 Hamming 距离，即与 Chromaprint 相同的比较方法。

## API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/stats | 库统计 |
| GET | /api/settings | 获取设置 |
| PUT | /api/settings | 保存设置 |
| GET | /api/library | 音乐库分页查询（支持 `search/sort/order/format/libFilter/scrapeTier`） |
| GET | /api/library/locate/:id | 返回某文件在（不含筛选的）全量音乐库中，按给定排序的位置索引，供前端跳页定位 |
| POST | /api/browse-folder | 弹出系统原生选择文件夹对话框，返回选中的绝对路径 |
| POST | /api/scan/start | 启动扫描（`steps` 数组决定运行哪些阶段，详见下方"扫描通道"） |
| POST | /api/scan/pause | 暂停当前扫描（在阶段边界处挂起，保留进度） |
| POST | /api/scan/resume | 恢复已暂停的扫描 |
| POST | /api/scan/abort | 停止扫描 |
| GET | /api/scan/stream | SSE 进度流 |
| GET | /api/duplicates | 重复组列表（`?resolved=0/1`） |
| GET | /api/duplicates/:id | 重复组详情 |
| POST | /api/duplicates/:id/resolve | 确认删除 |
| POST | /api/duplicates/resolve-all | 批量确认 |
| PUT | /api/duplicates/:id/tracks/:fid/keep | 手动覆盖 |

### 扫描通道（`/api/scan/start` 的 `steps`）

三条通道相互独立，互不触发对方的提取逻辑：

| 通道 | steps | 会做什么 |
|------|-------|----------|
| 基础匹配 | `enum, meta, match` | 枚举目录 → 元数据智能更新 → 仅按标题/艺术家/时长等元数据匹配 → 更新重复组。不触碰声纹、不触碰刮削 |
| 声纹匹配 | `enum, meta, fp, match` | 在基础匹配之上，智能提取声纹（按 `file_mtime` 跳过未变化文件）→ 重新匹配 |
| 刮削匹配 | `enum, meta, scrape, match` | 在基础匹配之上，向 MusicBrainz/AcoustID 智能刮削（仅刮削未刮削过的文件）→ 重新匹配 |
| 智能执行全部 | `enum, meta, fp, scrape, match` | 依次执行以上三条通道 |

声纹相似度阈值、时长容差、音质优先级的修改只影响 `match` 阶段本身，不会触发重新提取声纹——在"扫描"页对任意通道点智能执行（或在"设置"页点重新匹配提示条上的按钮）都只会重新比对，不重新提取。

## 项目结构

```
musicdedup/
├── server.js        # Express 入口 + 所有 API 路由
├── lib/
│   ├── db.js               # SQLite (WASM) schema + 查询

│   ├── chromaprint-bridge.js # 可选 fpcalc 调用封装（供 AcoustID 查询用）
│   ├── scanner.js          # 文件扫描 + 元数据/声纹提取，含暂停/停止钩子
│   ├── scraper.js          # AcoustID / MusicBrainz 刮削
│   ├── tier.js             # 刮削分类（绿/黄/蓝/红）判定
│   ├── matcher.js          # 多阶段重复检测
│   ├── rules.js             # 保留规则引擎
│   ├── tagger.js            # 标签读写调度 + 写入历史
│   └── flac-writer.js / m4a-writer.js / ogg-writer.js  # 原生纯 JS 标签写入器（FLAC/M4A/OGG，无需 exiftool）
├── public/
│   ├── index.html   # 入口 HTML
│   └── app.js       # React SPA
├── data/            # SQLite 数据库（运行后自动创建）
└── README.md
```

### v1.9.1

**重要修复：跨歌曲误判为重复（数据安全相关）**
- 排查"多首完全不同的歌被合并成一个重复组"的报告后，找到了根因：上一版把时长分组阶段的分组人数上限从 200 提高到 600 后，纯粹依赖声纹比特相似度、且完全没有独立佐证的两两比较数量随分组人数增大而平方级增长——只要出现哪怕极少量的巧合式高相似度，配合并查集的传递性，就能把好几首完全不相关但时长接近的歌连成一串。已用构造数据复现（92% 声纹相似度、标题艺术家完全不同的两首歌）并确认修复有效：现在声纹前缀分组/时长分组/MusicBrainz 确认这三处，只要相似度没有高到 97% 以上（基本可以确定就是同一份音频），就必须标题或艺术家本身也有一定文本重合度作为独立佐证才会判定为重复；真正的同曲目重复（标题、艺术家一致）不受影响。

### v1.9.0

**实验性：Chromaprint 本地重复匹配**
- 新增第五阶段匹配：如果配置了 fpcalc，声纹匹配阶段会额外用 Chromaprint 指纹做一次独立的本地重复比对——与本程序内置的频谱声纹（Goertzel）并行运行、互不影响，不会互相覆盖。命中的重复组会标注新标签「Chromaprint确认」，与既有的「声纹一致/声纹相似/声纹不同/MusicBrainz确认」等标签并列显示、可在重复组页面按标签筛选。
- 目的是让你能直接对比两种指纹方法的实际效果（各自发现了哪些重复组、有多少是两者都找到的交集），再决定要不要正式采用；这一版本身不改变现有判重结果，只是新增了一路独立的比对与标注。
- fpcalc 未安装/未配置时该阶段自动跳过，不影响其余功能，本地判重照常只用内置频谱声纹（默认开箱可用）。
- 技术细节：为了避免自行实现容易出错的 Chromaprint 压缩指纹解码算法（沙盒环境下没有真实 fpcalc 可交叉验证正确性），改为让 fpcalc 额外跑一次 `-raw` 模式拿到未压缩的原始指纹用于本地比对，原本给 AcoustID 用的压缩指纹不受影响——声纹提取阶段的耗时会因此增加（仅限已配置 fpcalc 的用户）。

**MB 刮削"精确/模糊"占比失真**
- 修复了一个让 MusicBrainz 刮削结果几乎全部显示"精确匹配"、模糊匹配几乎不可能出现的判定 bug：原来只要文件有时长信息（几乎所有文件都有）就被当作"证据充分"直接判为精确，时长本身其实是很弱的佐证。现在"精确"需要真正的佐证——专辑名对得上，或者时长高度吻合且标题相关性打分很高——否则归为模糊匹配，更贴近实际情况。

**其它**
- 确认"强制全量重扫"已经在扫描页的「高级」按钮之后，不会默认展示。

### v1.8.2

**定位到音乐库/播放器定位——真正的根因**
- 用自动化端到端测试（jsdom 实际执行 app.js + 真实点击）复现后，找到了三份定位反馈背后共同的根因：音乐库/重复组/白名单/写入历史四处的行 DOM 引用表（`rowRefs`/`groupRefs`）只在挂载时写入，卸载时从不清理。改变排序、切换筛选、甚至只是数据重新拉取一次，都会让旧行被卸载，但引用表里的旧记录不会被移除——它指向的是一个已经从页面上摘除的"陈旧"元素。下次定位时代码看到"这个 id 有记录"就直接调用 `scrollIntoView`，浏览器对一个不在文档里的元素调用它是安静地什么也不做——代码以为成功了，实际上界面纹丝不动。这解释了"排序一改动定位就再也不管用"和"筛选状态下定位失效"两个现象，是同一个 bug。现在卸载时会正确清理引用，并且在使用前额外检查 `isConnected`，双重兜底。已用自动化测试验证：切换排序、来回切换后，定位依然生效。

**AcoustID——找到真正病因**
- 上一版新增的诊断信息立功了：实测显示 AcoustID 返回的是 `api-error-4:invalid API key`。之前的代码把"无效 Key"的错误码错记成了 3，实际是 4——这不仅让批量刮削的失败判断走错分支（一直不会触发提前中止，白白刷完整个曲库），更严重的是**设置页的 Key 验证功能本身就用错了同一个错误码**，导致一个真正无效的 Key 会被误判为"验证通过"。现在改为按错误信息文本（"invalid API key"）判断，不再依赖具体数字，两处一起修复。如果你之前"验证通过"但刮削一直 0 命中，很可能就是这个原因——请重新验证一次 Key，并确认使用的是 acoustid.org/my-applications 申请的应用/client 密钥，不是 acoustid.org/api-key 页面看到的个人密钥。

**播放卡死自愈**
- 新增卡顿自动恢复：当播放出现缓冲卡死（`waiting`/`stalled`）超过 4 秒仍未恢复，或播放器报错（`error`，最多重试 3 次），会自动在当前进度重新建立底层网络连接并继续播放——相当于把"切歌再切回来"这个手动解决办法自动化了。

**刮削分类——繁简忽略开关的一个遗漏**
- 排查确认：`ignore_script_variant` 开关虽然已经接入了"标题/艺术家/专辑是否算精确匹配"的判断，但判断"是否还有值得推荐写入的字段"这一步里，专辑字段的比较仍然是不做繁简折叠的裸比较——导致像"看我72变/看我72變"这种纯繁简写法差异，在繁简忽略开启时依然被算成"有可写入字段"，分类停在蓝色（精确匹配可写入）而不是绿色。现已修正为同一套繁简感知比较。
- 同时修复了刮削弹窗里专辑字段的推荐文案：之前对任何文本差异都统一说"精确匹配，建议覆写"，包括单纯繁简写法不同的情况，读起来自相矛盾（"精确匹配"却要"覆写"）。现在纯繁简差异会显示"仅繁简写法不同，与文件属性一致"；真正的文本差异（非junk专辑名）显示中性的"与文件属性不同，请手动确认"（不再默认给出"推荐"标记），语气和标题/艺术家保持一致；专辑名疑似非正规（junk）时依然会明确推荐覆写，这是唯一还保留"建议"措辞的分支。

**刮削筛选下拉框样式**
- 与"格式"筛选框统一宽度、留白与配色（不再随选中分类变色，也去掉了 🟢🔵🔴 emoji）。
- 蓝色分类文案由"精确匹配 · 有缺失"改为"精确匹配可写入"。

**时长分组阶段的静默遗漏**
- 排查动画原声一类短促曲目（40 秒左右的过场/主题曲）漏配的报告时，发现时长分组阶段里超过 200 首的分组会被直接跳过、且没有任何提示——曲库里短时长曲目一多就很容易触发。现在上限提高到 600（该阶段每次比较开销很小，可以承受），且跳过时会在完成消息里报告跳过了多少个超大分组，不再是无声的遗漏。这不保证一定能解决"没匹配为重复"的具体案例（如果两个版本的实际音频内容本身有差异，无论如何都不会被判定为重复），但修的是一个真实存在的静默 bug。

**文件属性面板**
- 新增"流派"字段。
- 原来的"声纹方法"拆成两行：本地声纹（本程序内置的去重算法，无需外部工具）与 AcoustID 声纹（通过 fpcalc 生成的 Chromaprint，仅用于查询 AcoustID），避免两种完全不同用途的指纹被混在一个含糊的字段里。

### v1.8.1

**播放来源定位——修复竞态条件**
- v1.8.0 的"定位到音乐库"上线后实际不生效：重置筛选状态会触发音乐库自身的自动加载副作用，与定位逻辑自己的翻页请求并发竞争，后者的正确结果常被前者的默认第 1 页数据覆盖。现在定位过程会临时抑制这次自动加载，两者不再互相打架。

**扫描页暂停/继续/停止按钮消失**
- 根因在后端：扫描过程中每条进度广播只发送了 `{phase,pct,message}`，未合并 `running`/`paused` 等状态字段，前端整体替换 `status` 后 `status.running` 几乎立刻变成 `undefined`，导致依赖它显示的暂停/继续/停止按钮在扫描开始一瞬间后就消失（`GET /api/scan/status` 也因此一直卡在初始的"准备中 0%"）。现在进度事件改为合并进 scanState 后再广播，按钮与状态查询都能正确反映扫描中/已暂停。

**AcoustID 排查**
- 改用官方推荐的 POST 方式提交查询（原先的 GET 在指纹较长时更容易受 URL 长度/代理层限制影响）。
- 修复了一个可能是真正病因的问题：之前只要 HTTP 状态码不是 2xx 就直接判定失败、从不读取响应体——但设置页的 Key 验证功能明确证明 AcoustID 会在非 200 状态下依然返回结构化 JSON 错误信息；现在无论状态码如何都会先尝试解析 JSON，只有解析失败时才归为纯粹的 HTTP 错误，这样能看到 AcoustID 真正返回的错误内容，而不是笼统的「http-400」。
- 中止提示补充了最近几次失败的具体错误详情，不再只是笼统的「限流/网络错误」。
- 新增专辑年份校正：MusicBrainz 的 recording 搜索接口返回的 releases 列表有时并不完整（可能不含最早的原版专辑），导致"选年份最早的正式版"这条规则挑出的其实是"搜索结果里最早的一个"，而非真正最早的官方发行。现在对已确认精确匹配、且文件带专辑标签的情况，会额外用该 recording 的完整发行列表校正一次年份/专辑信息。

**刮削写入推荐勾选**
- 修复了标题/艺术家/专辑在精确匹配甚至模糊匹配时被默认勾选写入的问题——这三项永远只给"推荐"提示，不自动勾选，需要手动确认后才会写入。

**刮削分类逻辑统一（重要变更）**
- 排查发现"筛选显示一种分类，曲目自己标注的又是另一种分类"的根因：筛选走的是服务端 `lib/tier.js`（真实 opencc-js 繁简词典），而列表行图标和刮削弹窗走的是前端另一份不完整的手写繁简对照表（缺字，比如"藉"“鐘"），两边不是同一套算法，自然会对不上。
- 现在只有一套实现（`lib/tier.js`），服务端在 `/api/library`（含分页普通路径）和 `/api/files/:id/scraped` 里都会算好 `scrape_tier` 一起下发，前端不再自己重算，筛选 / 列表图标 / 刮削弹窗徽标三处保证完全一致。
- 按新需求把刮削分类从四档精简为三档 + 未刮削：🟢 精确匹配（标题/艺术家/专辑完全一致，无缺失字段）、🔵 精确匹配 · 有缺失（一致但有字段建议补全）、🔴 模糊匹配（任一字段不一致，或匹配依据非精确）、⚪ 未刮削。原来的"繁简模糊匹配"档位不再单独存在，改为下面的开关控制。
- 设置页新增「刮削分类 · 繁简忽略」开关（默认开启）：开启时标题/艺术家/专辑的一致性判断会先做繁简折叠（如"回到过去"/"回到過去"视为一致）；关闭后繁简不同会被计入「模糊匹配」。这是纯展示层的判断规则，切换后下次加载即生效，不需要重新扫描。
